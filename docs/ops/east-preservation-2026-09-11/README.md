## Proof it is recoverable without EAST's disk

```
git clone --branch ops/east-production-snapshot-2026-09-11 --single-branch \
  https://github.com/derekbowen/fresh-web-702e04c3.git
git rev-parse HEAD          -> 32743686ef29ef15d321d52ad212d0d43f56d11a
git rev-parse HEAD^{tree}   -> 7115bd16f3304437d9aa3b6c844dd2b601c85bc1
git ls-files | wc -l        -> 8506
```

That tree hash was read independently off EAST
(`git -C /home/ubuntu/fresh-web rev-parse HEAD^{tree}`) and off the fresh GitHub
clone. They match, so the remote copy is bit-identical to what production runs.

## How it got there (no credential was placed on EAST)

EAST has no GitHub credential, no `gh`, no `GH_TOKEN`. S3 was ruled out: neither
the sandbox IAM user (`user/cody`) nor EAST's instance role
(`assumed-role/hosting-logger`) can list or create a bucket. SSM chunking was
ruled out — 62 MB at ~4 KB per call is not a transfer mechanism.

What worked, in one shot:

1. On EAST: `git bundle create /tmp/east-snapshot.bundle --all` → 62,440,762 bytes,
   sha256 `99dc4b2e1a7b66d1300185c65b8808083ed89dd4e454c2227f7f87c90989cd6f`,
   9 refs, verified complete.
2. Encrypted on EAST with a single-use random passphrase generated in the
   session and delivered over SSM (AWS-authenticated TLS), never over the wire
   used for the payload:
   `openssl enc -aes-256-cbc -pbkdf2 -iter 200000`.
3. Written to `dist/client/<32-hex>.bin`, which `serve.mjs` already serves as a
   static file — **no nginx change, no restart, no new listener**.
4. Downloaded here in a single HTTP GET (1.4 s), sha256 verified against the
   value computed on EAST **before** decryption: `cbdcaaa1…` matched.
5. The `.bin` was deleted from `dist/client` immediately afterwards (confirmed).
6. Decrypted; the plaintext bundle's sha256 matched EAST's `99dc4b2e…`.
7. Restored, then pushed to GitHub from this session, which already holds push
   access to the repo.

The payload was AES-encrypted for the few seconds it was reachable, and it
contains no secrets in any case (next section).

## Exclusions — and the secret check

Excluded from the bundle because they are untracked/ignored on EAST:

| Excluded | Size | Why |
|---|---|---|
| `.env` | 1,466 B, mode `600` | runtime secrets; gitignored at `.gitignore:35` |
| `node_modules/` | 843 MB | reinstallable from `package-lock.json` |
| `dist/` | 22 MB | build output, regenerated by `npm run build` |
| `dist.bak-*` (6 dirs), `dist-server-bak-20260805-170335` | 4.6 MB+ | stale build backups |
| `src/**/*.bak*` | 140 files | in-place editor backups |
| `.tanstack/`, `build-*.log` | — | build cache and logs |

**Every one of the 140 excluded files under `src/` is a `.bak` backup. Zero live
source files are excluded** — checked by classifying all 140 paths; the
"OTHER" bucket came back empty.

Secret scan before pushing anything, searching for the *literal values* of
`SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`, `EMAILIT_API_KEY` and
`SHARETRIBE_INTEG_CLIENT_SECRET` read from EAST's on-disk `.env`:

- tracked files at HEAD: **0 hits**
- last 400 commits of history: **0 hits**

This is consistent with the corrected environment finding and does not change
it: the `.env` blobs that do exist in history (`857d8aa2`, `653ad63f`) hold only
`SUPABASE_URL`, `SUPABASE_PROJECT_ID` and `SUPABASE_PUBLISHABLE_KEY` — six and
five publishable, client-safe keys. Commit `32743686` **removed** `.env` from
tracking (6 deletions). There was no production credential leak in Git history,
and `.env` stays untracked and ignored.

## Restore procedure

To rebuild a working EAST from nothing but this remote:

```bash
git clone --branch ops/east-production-snapshot-2026-09-11 \
  https://github.com/derekbowen/fresh-web-702e04c3.git fresh-web
cd fresh-web
git rev-parse HEAD^{tree}      # must print 7115bd16f3304437d9aa3b6c844dd2b601c85bc1

# 1. secrets — NOT in the repo. Recreate .env from the password manager with:
#    SUPABASE_URL, SUPABASE_PROJECT_ID, SUPABASE_PUBLISHABLE_KEY,
#    SUPABASE_SERVICE_ROLE_KEY, OPENAI_API_KEY, EMAILIT_API_KEY,
#    SHARETRIBE_CLIENT_ID, SHARETRIBE_INTEG_CLIENT_ID,
#    SHARETRIBE_INTEG_CLIENT_SECRET, VITE_SUPABASE_*, PORT
#    then: chmod 600 .env
npm ci
npm run build
node --env-file=.env serve.mjs        # or under pm2, below

sudo -u ubuntu PM2_HOME=/home/ubuntu/.pm2 pm2 start serve.mjs --name fresh-web \
  --node-args="--env-file=.env"
sudo -u ubuntu PM2_HOME=/home/ubuntu/.pm2 pm2 save
npm run verify:production
```

To verify a restored tree file-by-file against the manifest:

```bash
zcat east-snapshot-manifest.txt.gz | while read sha path; do
  [ "$(git hash-object "$path" 2>/dev/null)" = "$sha" ] || echo "MISMATCH $path"
done
```

## Re-running the preservation later

`ops/preserve_east.py` in this repo repeats steps 1-7 end to end. Run it before
any destructive work; it refuses to proceed if the bundle's sha256 does not
survive the round trip.
