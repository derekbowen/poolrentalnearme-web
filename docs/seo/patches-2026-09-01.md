# EAST (`fresh-web`) patch proposals — 2026-09-01 GSC recovery audit

Companion to `gsc-recovery-2026-09-01.md`. The marketing site lives on EAST
(`/home/ubuntu/fresh-web`, TanStack Start, pm2 as `ubuntu`) and is not in this
repository, so these are proposals with exact anchors, not applied diffs. Every
item was verified against the source on EAST or against the live response on
2026-09-01/02. None of these is applied. Nothing here changes production data,
legal text, or GSC settings.

Deploy for any of them: patch the file(s) → `npm run build` →
`sudo -u ubuntu PM2_HOME=/home/ubuntu/.pm2 pm2 restart fresh-web` → re-crawl the
touched sitemaps (`scratchpad/crawl_all.py` → expect 0 redirects, 0 noindex,
byte-stable index).

Legend: **Safe** = generator/template change, reversible, no URL changes.
**Needs Derek** = business-claim or policy wording; house rule 1 / rule 5 apply.

## S4 · Stop fake `lastmod` — Safe, P1 (highest value of the safe set)

Three sources of fabricated freshness, all verified:

1. `src/routes/sitemap[.]xml.ts:45-54` — the index entries for
   `sitemap-static.xml` and `sitemap-pages-comparisons.xml` use
   `lastmod: new Date()`, so the sitemap index is never byte-stable.
   Change: omit `lastmod` on those two entries.
2. `src/lib/sitemap.ts:197` — per-URL `lastmod: row.updated_at`. `updated_at`
   is bumped by `trg_content_pages_updated_at` on **any** column write,
   including the monthly related-slug refresh.
   Change: select `content_refreshed_at` (add the column if absent; backfill
   once from the last genuine content write, or leave NULL) and emit
   `lastmod` only when it is non-null. Never fall back to `now`.
3. Supabase pg_cron `refresh-related-slugs-monthly` (`0 3 1 * *`,
   migration `20260520091701_…sql`) calls
   `refresh_related_slugs_for_template('host_acq_city')` and `('host_acq_city_es')`,
   rewriting `related_slugs` on ~4,452 rows and therefore re-stamping
   `updated_at` on the 1st of every month at 03:00 UTC (observed 2026-09-01).
   Change: have that function set `updated_at = updated_at` (or wrap the
   update with the trigger disabled) so link-block maintenance is not
   reported to Google as a content change. This is a Supabase migration on the
   content project; it is not a production-data change in the sense of the
   brief, but I will not run it without a GO.

Verify: two consecutive fetches of `/sitemap.xml` are byte-identical; the
host-acquisition sub-sitemap's `lastmod` values stop clustering on the 1st.

## S10 · `robots[.]txt.ts` on EAST — Safe, P3 (hygiene)

`src/routes/robots[.]txt.ts` emits `Allow: /s$`, `Allow: /s`, `Disallow: /s?`.
On www this route is **not** what Google reads — WEST serves
`/var/www/html/robots.txt` (which disallows only `/s?*&page=`). The EAST
version is reached only on non-www origins. Make the two files identical so a
future origin change cannot silently flip the search route's crawlability;
and per report §4, do not use robots to noindex `/s?address=` — that is a
migration decision (N6).

Also: the `.bak-noins-20260817-*` and `.bak-ins2` copies beside the comparison
route files still contain the pre-Aug-17 insurance text (Hartford, $2M/$4M,
STRETCH). They are not built or served (verified live 2026-09-02: the Giggster
page's only "$2M" mentions describe Giggster's COI requirement). Move them out
of `src/routes/` so a future glob-based build or grep cannot resurrect them.
