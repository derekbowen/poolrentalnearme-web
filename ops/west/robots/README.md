**Status: nothing has been installed.** No server, nginx, Cloudflare or database
change was made. Everything here was produced from read-only `GET`/`HEAD` requests
on 2026-11-15 (UTC) and from the code in this repository. The proposed file is a

## Running the tests

```
node --test ops/west/robots/*.test.mjs          # 269 tests, offline, < 1 s
ROBOTS_LIVE=1 node --test ops/west/robots/robots.proposed.test.mjs
                                                # also fetches today's sitemaps (16 GETs, ~15 s)
```

Needs Node 18+ and nothing else (no `node_modules`). Name the test files (the glob
above). Node 22 does not expand a bare directory argument (`ops/west/robots/`) into
its test files; that form used to fail with MODULE_NOT_FOUND and run nothing. It now
works through `index.js`, which imports the three test files (a test keeps that list
in step with the directory), but the glob stays the documented form, and a test
checks that every run command written in these files and in the ops record uses it.

Result on 2026-11-15, Node v22.23.4 (after the review fixes): 269 tests, 268 pass,
0 fail, 1 skipped (the live run, which is opt-in); with `ROBOTS_LIVE=1`
`robots.proposed.test.mjs` passes 91 of 91: 16 sitemap files, 10,074 distinct URLs,
126 of them listings, none blocked by the proposed file and none blocked by the live
file. The sitemap files themselves (`/sitemap.xml` and the 15 children its index
lists, `?page=2..4` of the host-acquisition sitemap among them) are checked too:
offline from `fixtures/sitemap-files.www.poolrentalnearme.com.2026-11-15.txt`, and in
the live run against whatever the index lists that day. A crawler does not follow a
sitemap it is not allowed to fetch, so a rule such as `Disallow: /*page=` would hide
those children while every URL inside them still looked allowed.

## 2. How Google reads the live www file

Read with `robots-match.mjs`, which implements the rules on
<https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt>
(page read 2026-11-15, dated "Last updated 2026-10-23 UTC").

- 18 groups: 17 named crawlers, each alone in its group, and `*`.
- There is no `Googlebot` group, so Googlebot follows `*`. So does every unnamed crawler.
- The `*` group has 22 rules: `Allow: /` (line 51) through `Disallow: /s?*&page=`
  (line 87). `Crawl-Delay: 5` (line 82) sits in the middle of it; Google ignores the
  line and it does not end the group.
- The file ends with `User-agent: Claude-SearchBot` / `User-agent: CCBot` groups.
  The very last line, `Disallow: /host/preview/`, belongs to the CCBot group.

For comparison, URLs the live file allows: `/s` 200 `index, follow`;
`/s?address=Austin%2C%20TX`, `/s?page=2`, `/s?pub_poolAmenities=hot_tub` 200 with
`noindex, follow` in both header and meta; `/login` and `/recover-password` 200 with
meta `noindex, follow`; `/dashboard` 200 with meta `noindex, nofollow`; `/signup` and
`/confirm` 200 `index, follow`; `/u/<uuid>` 200 `index, follow`; a listing 200
`index, follow`.

What this shows:

1. **The claim holds for the search route and for `/p/p/`.** Every `/s?…` URL fetched
   answers 200 with `noindex, follow` twice. A crawler that is told not to fetch
   `/s?…&page=N` never sees that. `/p/p/…` answers 301 and a crawler told not to
   fetch it never sees the redirect.
2. **It does not hold for the signed-in routes, and that is a reason to keep those
   rules.** `/profile-settings`, `/account…`, `/inbox`, `/l/new`, the listing
   edit/checkout/draft variants, `/verify-email`, `/preview` and `/host/preview/start`
   answer 200 with an empty page and **no** noindex at all when not signed in, and
   `/reset-password` answers `index, follow`. For these, robots.txt is the only thing
   keeping them out of the crawl. Giving them a `noindex` header belongs in the app
   (auth routes — out of scope for this change) and would be worth doing before any
   of these rules is ever relaxed.
3. `/inbox/orders`, `/order/<id>`, `/sale/<id>` and `/listings` do carry
   `noindex, nofollow`, but they are private pages; the owner's principle keeps them
   blocked.

## 4. The proposed file

`robots.www.poolrentalnearme.com.proposed.txt` is the live file with these edits and
no others (`diff` the two files to see them). The principle, from the owner: do not
block crawling of a URL whose only protection is a directive the crawler has to read;
do keep blocking private and action URLs.

| Edit | Change | Fixes | Proof (`robots.proposed.test.mjs`) |
|---|---|---|---|
| **E1** | `Disallow: /host/preview/` moved from the end of the file into the main group. | L1 | `FIXED (E1): /host/preview/x is disallowed (live file: allowed)`; `the only thing newly blocked for Googlebot is /host/preview/ (E1)` |
| **E2** | `Disallow: /p/p/` removed (replaced by a comment saying why). | L2 | `FIXED (E2): /p/p/anything is allowed (live file: disallowed)` |
| **E3** | `Disallow: /l/new` → `Disallow: /l/new$` and `Disallow: /l/new?`. | L6 | `FIXED (E3): /l/new-heated-pool/<uuid> is allowed…`; `/l/new is disallowed`; `/l/new?utm_source=x is disallowed`; `listing URLs /l/<slug>/<uuid> are allowed whatever the slug starts with` |
| **E4** | `Disallow: /auth` → `Disallow: /auth$`, `Disallow: /auth?`, `Disallow: /auth/`. | L7 | `FIXED (E4): /author/x is allowed…`; `/auth`, `/auth?redirect=…`, `/auth/x` still disallowed |

Two comment lines were added (why `/p/p/` is not blocked; that Google ignores
`Crawl-Delay` and that `/s?page=N` is not matched), and the two comment headings over
the crawler lists were reworded because the old first heading ("Block aggressive
scrapers and AI crawlers") sat over crawlers that are allowed.

Guard rails in the tests: `the cases that change are exactly the ones marked with an
edit`; `every "Disallow" of the live "*" group is still there, narrowed or moved only
where an edit says so`; `the Sitemap lines are unchanged`; and every sitemap URL is
allowed for Googlebot, an unnamed crawler and GPTBot.

Side effects to know about:

- **E5** makes the twelve welcome crawlers subject to every rule of the main group,
  including `Disallow: /s?*&page=` and, for any of them that honours it,
  `Crawl-Delay: 5`. Today none of that applies to them. It also relies on the crawler
  understanding several `User-agent:` lines on one group; Google documents this, how
  each third-party crawler's parser behaves was not tested.
- **E6** makes bare `/order` and `/sale` crawlable. Neither is a route: both answer
  404 with `noindex` today.
- **E4** makes any path that starts with `/auth` but is not `/auth`, `/auth?…` or
  `/auth/…` crawlable (for example `/author/…`). No such path is known today.
- **E2** lets crawlers fetch `/p/p/…`. All three URLs tried answered 301 in one hop.

For the twelve welcome crawlers the live file allows every row, except that CCBot is
already disallowed from `/host/preview/x` (its group carries that one rule, L1); the
proposed file gives them the "Proposed file" column (E5). So for CCBot, E5 adds the
private-URL rules but not `/host/preview/`, which it had already. MJ12bot, AhrefsBot, Bytespider,
Baiduspider and Yandex are blocked from everything in both.

## 6. The live file compared with what the two apps would generate

Neither generator produces the live file.

**This repo — `server/resources/robotsTxt.js` + `server/resources/robots.txt`.** Routed
at `/robots.txt` in `server/index-prod.js`, but nginx answers that path first on www.
If it were served it would differ from the live file like this (tests under
`reference: the marketplace app's own robots.txt`):

- One `*` group and nothing for named crawlers: the five blocked crawlers would be let in.
- `Disallow: /s` blocks the whole search route including bare `/s` (live allows `/s`
  and `/s?…` except `&page=`), and because it is a prefix it also blocks
  `/sitemap.xml`, `/sitemap-index.xml`, `/signup` and `/static/…`.
- `Allow: /p/` (redundant); `Disallow: /search`; `Disallow: /account/` and
  `Disallow: /admin/` with a trailing slash (so bare `/account` and `/admin` are
  allowed, where live blocks them); no `/auth` rule.
- `Disallow: /host/preview/` is inside the group there, so it does bind to everyone.
- `Sitemap:` becomes `<root URL>/sitemap-index.xml` instead of `/sitemap.xml` and
  `/public-pools.xml`. (`/sitemap-index.xml` answers 200 XML on www today.)
- Headers: `Cache-Control: public, max-age=86400`.
- The built-in fallback string (used when the file cannot be read) has no
  `/api/`, `/admin`, `/p/p/` or `/l/*/p/` rule and no Sitemap line.
- For a marketplace flagged private it serves `robotsPrivateMarketplace.txt`, which
  blocks `/l/` and `/u/` entirely.

**The other app — fresh-web `src/routes/robots[.]txt.ts`** (read from
`origin/ops/deploy-sha-enforcement`, commit `77028454`; not edited). For the www host
it would emit one `*` group that differs from the live file like this:

- `Disallow: /u/` — profiles blocked (live: allowed).
- `Allow: /s$`, `Allow: /s`, `Disallow: /s?` — **every** `/s?…` URL blocked, so none of
  their `noindex` headers could be read (live: only `&page=` blocked).
- None of the Sharetribe rules: `/l/new`, `/l/*/checkout|draft|pending-approval|new|edit`,
  `/order`, `/sale`, `/reset-password`, `/verify-email`, `/preview`, `/l/*/p/`, `/p/p/`
  are all allowed there.
- `/admin/`, `/account/`, `/auth/`, `/inbox/` with trailing slashes (bare forms
  allowed); `/verify/`; only `/api/sharetribe/` and `/api/public/track-city-click`
  under `/api/`.
- No named-crawler groups, no `Crawl-Delay`, one Sitemap line (`/sitemap.xml`).
- Headers: `Cache-Control: public, max-age=3600`, `X-Robots-Tag: all`.

`docs/seo/patches-2026-09-01.md` (S10) already asks for the www template in that app
to be made identical to the WEST file "so a future origin change cannot silently flip
the search route's crawlability". That is still open, and now there is a versioned
file to make it identical to.

**ccTLD files** (served by that generator; tests under `ccTLD files`): each is one `*`
group, `Disallow: /` plus `Allow:` lines for that country's pages, and a Sitemap line
for `/sitemap-country.xml` on its own origin. The bare and `www.` host of each country
serve the same rules and differ only in the Sitemap line. Every URL in each
`sitemap-country.xml` is allowed by that host's file. One defect, in the other
repository and not fixed here: **`/sitemap-country.xml` itself is disallowed** by
`Disallow: /` on all six hosts, and Google's documentation says a sitemap may be
followed "provided it isn't disallowed for crawling"
(`KNOWN DEFECT (ccTLD file, other app): <host> disallows the sitemap its own Sitemap line names`).
The fix would be an `Allow: /sitemap-country.xml$` line in that generator. Whether
Google has in fact fetched those sitemaps is unknown; Search Console's Sitemaps report
for each ccTLD property would show it.

## 7. Runbook — installing the proposed file on WEST

**Nothing below has been run.** It needs Derek's GO and access to WEST. It is an
nginx static-file swap, not a container release, so the image gate does not apply;
the swap is reversible in seconds.

Before touching the server:

1. `node --test ops/west/robots/*.test.mjs` passes, and
   `ROBOTS_LIVE=1 node --test ops/west/robots/robots.proposed.test.mjs` passes
   against that day's sitemaps.
2. `curl -s https://www.poolrentalnearme.com/robots.txt | sha256sum` still prints
   `3fa2699d…773cca`. If it does not, the live file changed after this snapshot:
   stop, re-capture, redo the diff.
3. Note the sha256 of the file being installed (`sha256sum robots.www.poolrentalnearme.com.proposed.txt`).

On WEST (through `ssm_runx.py`; the file is under 2 KB, far below the 9.5 KB payload limit):

```
# 1. Find the file nginx really serves for /robots.txt. Expected /var/www/html/robots.txt
#    (docs/seo/patches-2026-09-01.md) — confirm, do not assume.
sudo nginx -T 2>/dev/null | grep -n -B4 -A8 'robots'
F=/var/www/html/robots.txt            # replace with what step 1 shows

# 2. It must be the file versioned here.
sha256sum "$F"                        # expect 3fa2699ddf1a39e9...e32773cca
stat -c '%U:%G %a %y' "$F"            # note owner and mode

# 3. Back up OUTSIDE the web root (a .bak beside it would be publicly downloadable).
mkdir -p /home/ubuntu/robots-backups
sudo cp -p "$F" /home/ubuntu/robots-backups/robots.txt.$(date -u +%Y%m%dT%H%M%SZ)

# 4. Put the new file next to nginx, check it arrived intact, then swap atomically.
#    (ship robots.www.poolrentalnearme.com.proposed.txt to /home/ubuntu/robots.new first)
sha256sum /home/ubuntu/robots.new     # must equal the hash noted before
sudo install -o root -g root -m 644 /home/ubuntu/robots.new "$F.new"   # owner/mode as noted in step 2
sudo mv -f "$F.new" "$F"

# 5. nginx: nothing in the configuration changed, so this is a safety check plus a
#    reload in case nginx caches open files.
sudo nginx -t && sudo systemctl reload nginx

# 6. Verify at the origin, then through Cloudflare.
curl -sk --resolve www.poolrentalnearme.com:443:127.0.0.1 https://www.poolrentalnearme.com/robots.txt | sha256sum
curl -s https://www.poolrentalnearme.com/robots.txt | sha256sum
curl -sI https://www.poolrentalnearme.com/robots.txt | grep -i -E 'last-modified|etag|cf-cache-status'
```

Cloudflare caches `/robots.txt` at the edge for 600 s
(`docs/AUDIT_2026-09-17_cloudflare-impact.md`), so the public check can show the old
file for up to ten minutes. Wait it out; no Cloudflare change is needed.

**Roll back** — the same swap with the backup:

```
sudo install -o root -g root -m 644 /home/ubuntu/robots-backups/robots.txt.<stamp> "$F.new"
sudo mv -f "$F.new" "$F"
sudo nginx -t && sudo systemctl reload nginx
curl -s https://www.poolrentalnearme.com/robots.txt | sha256sum    # expect 3fa2699d...773cca after the edge TTL
```

After an install: re-fetch the live file into
`robots.www.poolrentalnearme.com.live.txt`, update its hash in `robots-cases.mjs`,
move the expectations in `robots.test.mjs` accordingly, and commit, so that this
directory keeps matching production. Google caches robots.txt for up to 24 hours
(per the page cited above), so the change is not immediate on Google's side; the
robots.txt report in Search Console shows the version Google holds.

## 8. Limits of this work

- Rules were evaluated with `robots-match.mjs`, not with Google's own parser. It
  implements what the documentation page states, and its header lists what it leaves
  out (typo tolerance, HTTP status handling). Percent-encoding follows RFC 9309
  §2.2.2, which the page cites: escapes of unreserved characters are decoded
  (`/%61ccount` is matched as `/account`) and other escapes are compared with
  upper-case hex, on both sides; the RFC's Figure 4 rows are unit tests. Whether
  Google's open-source parser also decodes, or only normalises hex case, was not
  checked. Neither www file has a `%` or non-ASCII character in a rule, so no verdict
  on the committed files depends on it. The
  set of characters allowed in a user-agent name (letters, `-`, `_`) comes from
  RFC 9309, which that page cites; that part of the RFC was not re-read. One visible consequence:
  `MJ12bot` is compared as `mj`. It still matches itself.
- How third-party crawlers (the AI crawlers, SemrushBot, Bing) parse the file was not
  tested. Only Google's documented behaviour is asserted.
- The nginx configuration was not read. The served path, whether nginx sets headers
  for `/robots.txt`, and what answers `/robots.txt` if the static file is removed are
  unknown until `nginx -T` is run on WEST.
- The fetch table is one sample per pattern, signed out, on one day.
